the problem

The fixes that don't fix it

Two-phase commit

Kafka exposes no XA resource to enlist. And even where 2PC exists, you buy a coordinator that must itself never fail — and pay it on every request.

Publish first, then save

Now the DB write can fail after the send. You didn't remove the lie — you picked the other one: an event for an order that never existed.

catch & retry the send

Helps with blips. But the process can die between commit and send — then there is no code left to retry, and no record that anything was owed.

The row and the event must live or die together — and exactly one transactional
system is in the room: the database. So put the event in the database.

Walk the three tombstones quickly — the audience has tried at least one of them.

  • 2PC: also throughput death; nobody runs XA against Kafka.
  • Swap order: symmetric failure, worse to debug (phantom events).
  • Retry: the killer is the crash between commit and send — kill -9, OOM, deploy. Nothing to retry.

fundamentals

Exactly-once delivery is a myth

Effectively-once processing is engineering.

  • After the ack is lost, both options are wrong — retransmit and you may duplicate, don't and you may lose. No protocol escapes this.
  • Kafka's exactly-once semantics are real — but scoped to read-process-write chains between Kafka topics. Postgres + HTTP + Kafka is outside that boundary.
  • So pick the honest transport — at-least-once — and make duplicates harmless instead of impossible.
at-least-once transport  +  idempotent processing  =  effectively-once outcome

This is the Two Generals problem wearing a Kafka t-shirt. Don't name-drop unless asked — the picture carries it.

Kafka EOS caveat matters for credibility: transactions + read_committed work great for Streams-style topologies. The moment a Postgres row or an HTTP 201 is part of the story, you're out of scope.

The green equation is the thesis — the rest of the talk is just implementing each side of the +.

the pattern

Happy path, end to end

The whole pipeline in nine beats. Step with → — no autoplay, no magic.

1. POST /orders arrives.

2. One transaction, two INSERTs — the order and its event. Atomic by construction.

3. Commit → 201. Note what has not happened: Kafka.

4. The relay wakes — adaptive 0.5–5 s — and claims NEW records, in key order.

5. send().get() — blocks until two of three brokers own the bytes.

6. Only then: NEW → COMPLETED, in a second, separate commit. Remember this seam.

7. Kafka delivers to shipping-service.

8. Consumer transaction: claim + shipment, one commit.

9. Offset commits last. So: a 201 means durably recorded & guaranteed to publish — not "already on the topic".

The centerpiece — 2½ min. Two beats deserve emphasis:

  • Beat 3: the request path ends before Kafka begins. That asymmetry is the whole pattern.
  • Beat 6: the separate COMPLETED commit — plant "remember this seam"; slide 18 harvests it (crash between 5 and 6 = duplicate).

Beat 9's sentence is lifted from the OrderController javadoc — it returns on the library-realities slide.

Routing — payload type → topic, key, headers

  • On the wire: key = orderId; headers carry eventType, eventId, traceId, spanId — duplicates are spottable in Conduktor without deserializing.
  • traceId is captured at schedule time by an OutboxContextProvider — the relay thread has no request context.

Casts trimmed for the slide (real code casts payload). If asked about Kotlin interop: builder route/defaults expose both Function1 and Consumer overloads — an expression lambda is ambiguous from Java, a block-bodied lambda resolves to Consumer. The braces are load-bearing.

Tracing point is a nice observability beat: schedule-time capture is the only way the eventual Kafka record correlates with the HTTP request that caused it.

producer

The relay — how the event actually leaves

  • Ordering lives here. stop-on-first-failure halts a failing key's queue — a later event for the same order can never overtake it.
  • The send blocks on the ack. send().get() on virtual threads — a returned send means replicated to ≥ 2 brokers.
  • Fail fast when Kafka is gone. max.block.ms=8000 hands the record back to the poller instead of parking a relay thread for two minutes.
  • Give up loudly. After 10 exponential retries the row goes FAILED — its own line on the dashboard.

This slide earns the Kafka-down demo: fail-fast + exponential retry is why that demo is snappy instead of a two-minute hang.

delete-completed-records=false is a demo choice — rows stay visible in psql. Production wants true or a purge job (slide 29).

Adaptive polling: tightens to 500ms under load, backs off to 5s idle — mention latency cost once, it returns on the when-not slide.

If asked "are those the defaults?" — no: trigger (fixed→adaptive), batch (10→20), retries (3→10), cap (1m→30s) and jitter (0→500ms) are overrides; stop-on-first-failure, delete-completed-records=false, the 2s initial delay and the ×2 multiplier ARE the defaults, restated so this slide reads from one file. inbox

The gap that remains — two seams no one can close

producer side — after the send

send to Kafka → broker ack ✓
⚡ crash here
UPDATE outbox_record → COMPLETED (separate commit)

on recovery the record is still NEW → sent again → a genuine duplicate on the topic

consumer side — after the work

DB tx commits — claim + shipment ✓
⚡ crash here
commit Kafka offset (separate step)

on rebalance Kafka redelivers from the old offset → a duplicate delivery to the handler

Both seams produce the same artifact — a duplicate. So one mechanism absorbs both →

This slide legitimizes the inbox. Neither seam is a bug: closing them needs an atomic commit across Postgres and Kafka — XA again, which doesn't exist here (the InboxGuard javadoc says exactly this).

Symmetry is the beauty: totally different failure points, identical downstream symptom, one cure. The green banner hands the mic to the ON CONFLICT slide.

inbox

The whole inbox is one statement

Check + write = one statement. SELECT-then-INSERT leaves a window two concurrent redeliveries will find — a rebalance lands the same event on two threads at once. Here, the loser of the race gets 0 rows from the database itself.

PK is (event_id, consumer) — not event_id alone. Several consumers fan out from one topic; each keeps its own ledger, so shipping processing an event never starves analytics of it.

The single most important slide of the inbox half. Read the SQL aloud — it takes ten seconds and it's the entire mechanism.

"The database is the referee": unique-constraint arbitration is the only dedup that survives concurrency, crashes, and rebalances with no extra coordination. Native query because JPQL has no upsert.

inbox

Consumer shape — claim, then act

claim() is @Transactional(propagation = MANDATORY) — calling it outside a transaction fails loudly. A self-committing claim could mark work done… that then rolls back. That's a lost event.

enable-auto-commit=false · ack-mode: record · concurrency: 3 — three threads racing is the normal case, not the edge case.

Every claim increments inbox.messages.processed or .duplicate — the Grafana panel you'll watch in the demos.

The pattern in one sentence: claim, then act, in one transaction — first delivery inserts+works+commits; duplicate returns early (offset commits, no second shipment); failure rolls back both (redelivery is a genuine first attempt).

Those three sentences ARE the three demos coming up. Say them here, prove them next.

inbox

Why this module is hand-rolled

  • namastack ships outbox only — there is no inbox / idempotent-consumer starter for Spring Boot 4 today.
  • The one first-party alternative — Spring Integration's IdempotentReceiverInterceptor + JdbcMetadataStore — drags you into channel adapters. You lose plain @KafkaListener.
  • So: a bespoke module. The entire mechanism is the one SQL statement you just saw — everything else is wiring.
  • Library discipline: no @EntityScan / @EnableJpaRepositories inside the module — either one would replace the host app's own scanning.

demo · poison pill

Poison → retries → DLT — no claim left behind

One bad event. Three questions: does it loop? does it lie? does it block?

1. The poison event reaches the handler first — two healthy events stuck behind it.

2. Transaction opens, claim inserts (uncommitted)… and the handler throws.

3. Rollback. The claim dissolves with the work — the event was never falsely marked handled.

4. Retry — 1 s later. Same story. And that's fine: no claim survived, so it's a clean slate.

5. Attempts 3 and 4 burn down. IllegalArgumentException would skip retries — this one is retryable.

6. The recoverer publishes to orders.v1.DLT — same partition, key ordering preserved.

7. Offset commits, the partition unblocks — the healthy events flow.

8. A separate group (shipping-service-dlt) watches the DLT — in production, that's an alert.

demo · ordering

One key, two API styles, two topics

Create, then cancel — the ordering story has a guaranteed half and an honest half.

1. Two API styles, two modules — one identical key. namastack queues per key.

2. The relay is strictly sequential per key: created leaves; cancelled waits. stop-on-first-failure keeps that queue honest even under errors.

3. Both land — same partition number, different topics.

4. Two topics = two consumer streams. The cancel can overtake the create.

5. The handler tolerates it — a WARN, not a crash. Per topic-partition: guaranteed. Across topics: tolerance is the design.

sharp edges · 1

Bugs I shipped in my own demo

The two keys that were "the same"

Comment & diagram claim Kafka key == outbox key. Reality: outbox key order-ORD-4F2A, Kafka key ORD-4F2A. Ordering survives — each is consistent per order — but the diagram lies, and anyone joining or deduping "on the key" gets burned.

The DLT that doesn't exist

The recoverer targets topic + ".DLT" — but only orders.v1.DLT was ever created, and auto-create is off. A poisoned cancellation has nowhere to go: the recovery path itself fails, silently, until the first bad cancel.

Retention is the dedup window

Inbox claims are purged after 7 days. Anything redelivered later is processed again — so inbox retention must stay comfortably above topic retention. An unbounded ledger is a slow-motion outage; a short one silently reopens the duplicate window.

All three were found by re-reading, not by tests. What the tests do pin — two slides ahead.

sharp edges · 2

Library realities

  • The metadata hides the record id. OutboxRecordMetadata exposes key, context, failureCount, attempt — not the outbox record id. So the idempotency key must live in the payload. Better anyway: the event id becomes part of the published contract instead of leaking infrastructure state.
  • 201 ≠ "on the topic". It means durably recorded and guaranteed to publish. SLAs, tests and UIs must not assume the event is already consumable — the relay publishes 0.5–5 s later.
  • The outbox table grows. Completed rows are kept here so demos can show them. The actuator module is a purge-only lever — DELETE /actuator/outbox/COMPLETED → 204 — there is no GET to inspect records with.
  • Deserialization is part of the contract. Without ErrorHandlingDeserializer, an unparseable payload throws inside poll() — before the listener, before any retry policy — and blocks the partition forever.

Each bullet is a "you'll hit this in week one" item.

  • Record-id point pairs with slide 13 — the eventId was born inside the producer transaction, which is exactly why replays carry the same id.
  • The deserializer bullet foreshadows nothing — it's the one failure mode we did NOT live-demo (needs a raw producer writing garbage bytes; mention Conduktor can do it if someone asks).

When not to do this

skip the pattern when…

  • Consumers share the database — read the table. No transport, no problem to solve.
  • Pure Kafka → Kafka pipelines — Kafka transactions / Streams EOS fit natively there.
  • You can't touch the writing code, or need every table change — that's CDC / Debezium territory: zero app code, but infra weight and capture lag.
  • Loss is genuinely acceptable — metrics, hints, cache warmers. At-most-once is cheaper.
  • Hard latency budgets — the poller adds 0.5–5 s before the event is even sent.

the ops bill you accept

  • two ledgers to purge — outbox rows and inbox claims — plus a dedup window to size
  • two curves to watch: backlog = never reached Kafka · lag = reached it, consumer behind
  • confusing those two sends you debugging the wrong service

The trust slide — recommending boundaries is what separates a pattern talk from a pitch.

Backlog vs lag deserves the extra beat: backlog is a producer-side metric from the outbox table; lag is a Kafka-side metric from the consumer group. Same symptom downstream ("nothing arrives"), opposite fixes.

Takeaways

1

Exactly-once delivery is a myth. Effectively-once is at-least-once + idempotency — engineering, not magic.

2

One local transaction per side: the producer commits row + event, the consumer commits claim + work. The database referees every race.

3

The sharp edges are the lesson: keys drift, DLTs go missing, retention is a semantic choice. Re-read your own demos.

The override that matters: max-retries defaults to 3 — on defaults, a dead cluster turns rows FAILED after ~14s of backoff (2+4+8), before the brokers even re-form quorum. Ten retries capped at 30s keep the relay trying for ≈3½ minutes.

Source: META-INF/spring-configuration-metadata.json inside namastack-outbox-core-1.9.0.jar — the artefact the build resolves, not the docs site. Property description confirms max-retries counts retry attempts after the first try.

Q&A ammo, "is 10 the default?": no — 3. The demo raises it because the kill-Kafka demo needs the relay still retrying after a multi-minute outage; on defaults the rows would give up while the brokers are still re-forming quorum (~20–30s), and slide 17’s "the recovery is the pattern" line would be a lie.

Worth saying if asked: stop-on-first-failure=true and delete-completed-records=false are defaults — the yml restates them for narration. And the routing fallback topic is a rename: outbox-events → domain-events.
